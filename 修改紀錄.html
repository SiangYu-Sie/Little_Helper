7. 本次修改 (階段 I) — 檔案層級

7.1 修改 HostSimTester.App/Pages/L1NormalScenarioPage.cs

解決 Multi Lot 分頁與 Normal Scenario 分頁的燈號互相影響、PJID 不顯示、Slot ID 計數異常、PJ1/PJ2 共用 CEID 誤學等 4 個問題。

  • Report 對應表分流：原 KnownReportByCeid 拆為 NormalReportByCeid 與 MultiLotReportByCeid 兩張表（uint → string），各分頁查各自的 CEID 對應。
  • 新增 ReportScope 列舉（Normal／MultiLot），由 tabControl.SelectedIndexChanged 切換 _activeReportScope。
  • 燈號／待處理動作／已學 CEID 全部 scope 化：
    • _reportLamps 改為 Dictionary<(ReportScope, string), Panel>
    • _reportActionByCeid 改為 Dictionary<(ReportScope, uint), string>
    • PendingReportAction 改由 _pendingReportActionByScope 字典支撐
  • Multi Lot 起始按鈕還原：新增 AddReportStartButton(...) helper — 外觀為藍色按鈕，但燈號仍註冊到 _reportLamps，按下時只把該動作標為 pending 並把燈號改為等待色，必須收到對應 S6F11 才會變綠。
  • PJID 提示：Multi Lot 的 PJ1／PJ2／Wafer Start／Wafer End／Complete 列旁加上可動態刷新的 PJID/SlotID hint label，於 PJ Create 對話框結束後立即更新。
  • Wafer Slot 進度：Multi Lot 的 Wafer Start／Wafer End 採用與 Normal 相同邏輯——Start 不累計、End 累計，必須所有 slot 完成才把 Start 與 End 兩盞燈一起轉綠；PJ1+PJ2 的 SlotMap 數量會自動加總成 _expectedWaferSlotCount。
  • PJ1／PJ2 共用 CEID 釐清：在 Multi Lot scope 中，僅暫時對應到當下動作，不會被永久寫進 MultiLotReportByCeid，避免後續 PJ2 事件被誤判成 PJ1。
  • L1 Normal 未開始前資料誤回填修正：修正尚未按下 Loading / Multi Lot 起始步驟時，背景收到其他流程或前次殘留的 S6F11 就直接把 CarrierID、SlotMap 寫到畫面並可能觸發事件燈號的問題；現在只有流程已透過 TrackExpectedReport 啟用對應步驟後，該步驟的資料與燈號才允許更新。
  • 輔助函式：ResolveScopedAction(normalActionText) 將 Normal 動作名稱依 _activeReportScope 對應到 Multi Lot 名稱；TryGetReportLamp(scope, actionText, out lamp) 改為以 scope 取燈；TryGetKnownReportAction(ceid, ...) 依目前 scope 選表。

7.2 修改 HostSimTester.App/Pages/L2ConcurrentRunPage.cs

對齊參考影像：該為按鈕的設成按鈕、不是按鈕的事件列保留為灰色等待列、移除影像中沒有的元素、補上影像中需要的輸入欄。

  • L2 Concurrent Run 測試設定確認：依舊工具 Concurrent Run LOG 與目前頁面流程，LOADPORT1 / Port1 對應 PJ1 Manual Start，LOADPORT2 / Port2 對應 PJ2 Auto Start。Port1 完成 CarrierIDRead、ProceedWithCarrier、SlotMap、Proceed SlotMap、Create PJ1/CJ1 後，PJ1 需停在 Waiting For Start，再由 Host 按 Start Process Job (PJ1) 送 S16F5 START；Port2 完成同樣 loading 流程並建立 PJ2/CJ2 後，PJ2 應由設備/ControlJob 自動 start，不需 Host 再送 S16F5 START。
  • L2 Concurrent Run PJID 預設與 Start 確認修正：修正 Start Process Job (PJ1) 送出 S16F5 START 時仍可能使用預設 PJ1，造成設備回覆 PROCESSJOB ObjectID(PJ1) does not exist 的問題；L2 Concurrent 預設 PJ/CJ ID 改為舊工具一致的 PJ001/PJ002、CJ001/CJ002，且 Start PJ1 前會開啟 PJ Command 視窗讓使用者確認實際 PRJOBID，送出的 S16F5 會以視窗中的 PJ ID 為準。
  • L2 Concurrent Run CJ 建立 payload 對齊舊工具：最新 LOG 顯示 S16F15 與 S14F9 均 ACK，但 S16F5 START 仍回 PROCESSJOB ObjectID(PJ001) does not exist；比對舊工具後修正 L2 Concurrent 的 S14F9 ProcessingCtrlSpec，CJ 建立時不再把 SlotList 帶入 PJ entry，SlotID 僅保留在 S16F15 的 PJ Material List，避免設備建立後 PJ/CJ 狀態與舊流程不一致。
  • S16F6 失敗判斷修正：補上 S16F6 ProcessJobCommand 回覆解析；當設備回覆 BOOLEAN False 或錯誤原因時，畫面會顯示 ProcessJobCommand: NAK/ERROR 並將該動作判定 FAIL，不再把 START/STOP/ABORT 命令失敗誤標為 PASS。
  • L2 Concurrent Run Proceed With Carrier 顯示修正：將 Port1/Port2 的 Proceed With Carrier 由原本旁邊的 Bypass CarrierID Event 小按鈕改為明確的 Send Proceed With Carrier 送出按鈕；CarrierIDRead 後自動送出或手動送出 S3F17 ProceedWithCarrier 成功時，會立即點亮對應列並在結果視窗留下 PASS 訊息，避免使用者看不出該指令是否已送出。
  • L2 Concurrent Run Port2 Queued 狀態顯示：Job Start 區新增 ControlJob 2 Queued 事件列，並將設備回報的 CJStatusChange_Queued 對應到該列，方便分辨 Port2 在步驟 10 後是已建立待排程，還是已真正進入 Auto Start。
  • L2 Concurrent Run Job 診斷訊息補強：在 Create PJ/CJ 與收到 S6F11 Job 狀態事件時，結果視窗會額外輸出 Port / PJID / CJID / Status 診斷訊息，方便快速判斷 Port2 是停在 Queued、已進 AutoStart，或 Port1 是否正確停在 WaitingForStart。
  • Loading & Job Start 測試方式釐清：1)/6) Carrier ID Read、3)/8) SlotMap Event、Job Start 區的 ControlJob/ProcessJob Start/Waiting 列皆為等待 Equipment 上報 S6F11；2)/7) Proceed With Carrier、4)/9) Proceed SlotMap、5)/10) Create ProcessJob & ControlJob、Start Process Job (PJ1) 為 Host 主動送出命令，分別對應 S3F17、S16F15、S14F9、S16F5，並以 S3F18、S16F16、S14F10、S16F6 回覆與後續 S6F11 事件驗證。
  • Job Processing 測試方式釐清：Job Processing 頁籤不是逐列送 Host command，而是在 PJ1/PJ2 start 後等待設備跑片過程依序上報 S6F11，包含 Recipe Start/Step Start、Chamber Start、E90 Wafer Start、E90 Substrate Location Changed Occupied/UnOccupied、Recipe Step End、E90 Wafer End、Chamber End、Recipe End、PJ/CJ End。驗證重點是事件內容中的 CarrierID、LotID、SlotID、RecipeID、PJID、CJID、LocationID 能正確對應前面建立的 Port/PJ/CJ/ContentMap。
  • 移除：各區塊頂端「藍色按鈕：主機主動命令／灰色列：等待設備事件」雙語圖例（AddStepLegend）。
  • 按鈕 vs 事件列確認（與影像逐項一致）：
